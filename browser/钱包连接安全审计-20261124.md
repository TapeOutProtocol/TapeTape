# 广场浏览器「连接钱包」功能安全审计

日期：2026-11-24　　版本：2.0.13（本机代码，**未提交、未对外发布**：官网下载仍是 2.0.11）

审计方式：五个角色**各自独立**只读审计同一份代码，互相看不到对方结论；汇总后我逐条对照代码核实，剔除误报。

| 角色 | 关注点 |
|---|---|
| 一、恶意网站攻击者 | 冒充、骗签名、骗交易、刷弹窗 |
| 二、密码学与签名正确性 | EIP-712 编码、消息签名、交易签名、链号 |
| 三、交易与资金安全 | 看到的和发出的是否一致、手续费、nonce、并发 |
| 四、移动端平台安全 | iOS / 安卓网页视图的来源判断、注入范围、生命周期 |
| 五、隐私、滥用与产品风险 | 身份暴露、刷接口、文案、合规 |

范围：`core/.../dapp.rs`、`browser/provider.js`、`ios/.../Square/DappWallet.swift`、`SquareView.swift`、`android/.../square/DappWallet.kt`、`SquareScreen.kt`，以及相关的 `chain.rs`、`files-backend/server.mjs`。

## 结论

**现在不能上线。** 底子是对的：签名摘要都在内核里算，拒绝盲签，子框架的请求一律拒绝，内核隔离没被破坏，签名原语经核对完全正确。

但有 5 条高危，都能让用户在「以为自己看清楚了、点的是对的」的情况下真的把钱转走。其中第 1、2 条攻击成本很低。

另有 9 条中危、十几条低危。

## 高危（上线前必须修）

### 高-1 显示的是 X Layer，实际可能发到 BNB 链（4 个角色独立发现）
- **位置**：iOS `DappWallet.swift` 第 160、171 行；安卓 `DappWallet.kt` 第 182、195 行。
- **问题**：估算交易时读一次「当前网络」，用户点确认后发送时又读一次。中间要联网估算，这段时间里网络可能被切换：网页同时请求切链，或用户自己在菜单里切。
- **攻击**：网页同时发「转 1 个原生币」和「切到 BNB 链」。用户先同意了切链，然后在交易弹窗上看到「X Layer · 1 OKB」，点确认后，实际在 BNB 链上发出 1 BNB。同一个接收地址，在 BNB 链上可能是攻击者的合约。
- **内核挡不住**：唯一的检查是「手续费涨一半就停」，但它拿两条链的手续费数字直接比，单位都不一样。
- **修法**：请求一进来就把链号定下来，估算、显示、发送都用这一个；内核发送时再核对链号和估算时一致。

### 高-2 弹窗可以被网页「调包」或叠加，用户点到的不是他看到的（4 个角色独立发现）
- **位置**：安卓 `DappWallet.kt` 第 115–120 行，新请求会把旧弹窗当作拒绝，然后原地换成新内容；iOS `DappWallet.swift` 第 232 行加 `Wallet.swift` 第 92 行，新弹窗会叠在最上面。
- **攻击**：先发一个无害的「签名登录」，算准用户要点确认的那一刻，换成交易或授权签名。按钮位置不变，用户这一下就批准了新的请求。网页还可以先用自己的 `confirm()` 弹「点确定领空投」，再让交易弹窗叠上来。
- **修法**：同一时刻只允许一个待确认的请求，后来的直接返回「已有请求在处理」（错误码 -32002），不替换、不叠加；每个弹窗带编号，按钮只回答自己那个；弹窗出现后，确认键锁住约 1 秒。

### 高-3 交易弹窗看不出代币授权、代币转账（5 个角色都提到）
- **位置**：`dapp.rs` 第 375–378 行；iOS 第 165 行；安卓第 187 行。
- **问题**：合约调用只显示 4 字节函数编号，比如「调用合约（函数 0x095ea7b3）」。钓鱼最常用的几种操作，在弹窗里看起来都是「金额 0、接收方是某个合约」，用户会以为无害：
  - `approve`：授权别人无限额度动你的代币；
  - `setApprovalForAll`：授权别人动你全部 NFT；
  - `transfer`：把代币转走。
- **修法**：内核解析常见函数，显示真正的收款方或被授权方，以及代币金额（按代币自己的小数位换算）。无限额度授权和 `setApprovalForAll(true)` 用红色警告，并要求二次确认。不认识的调用，提示「无法识别的合约操作」。

### 高-4 结构化签名（EIP-712）的确认框可以被欺骗（4 个角色独立发现）
- **位置**：`dapp.rs` 第 300–309 行；iOS 第 152 行；安卓第 172 行。
- **问题**：
  1. 确认框显示的是网页给的整段原始数据，按字母顺序排列，截到 1500 字。网页加一个名叫 `aaaa` 的超长字段，就能把被授权方 `spender`、额度 `value` 挤到看不见。
  2. 类型定义里没有的字段，也会显示，但根本没被签进去。网页可以借此写「本签名仅用于登录」。
  3. 「应用」一栏是网页自己填的，可以写成「TapeTape 官方」。
  4. Permit、Permit2（不用发交易的代币授权）、Seaport（NFT 挂单）这类一签就能被转走资产的签名，没有任何警告。
- **修法**：只显示按类型定义实际签名的字段，按定义顺序排列、不截断；有多余字段就拒绝；「应用」标注为「网站自称」；识别 Permit / Order 类签名，以及带 spender、operator 字段的签名，加红色警告。

### 高-5 结构化签名可以绕过链号绑定（角色一、二发现）
- **位置**：`dapp.rs` 第 293–299 行。
- **问题**：链号检查看的是网页给的 `domain` 对象，但真正参与哈希的是网页自己声明的 `EIP712Domain` 类型。网页声明一个不含 chainId 的类型，再在 domain 里写上正确的链号：检查能通过，弹窗也显示了，签名却没有绑定链号，可以拿到别的链上重放。
- **修法**：`EIP712Domain` 的字段必须和 `domain` 的键完全一致，并且必须包含 chainId。

## 低危（兼容性与细节）

- 结构化签名的格式校验偏宽松，和主流钱包（ethers / MetaMask）不一致：
  - 字符串 `"false"` 被当成 false 签，主流按 true 处理；
  - `uintfoo` 这类写错的类型被当成 256 位整数；
  - 结构体名可以叫 `address`，覆盖基础类型；
  - 奇数长度的十六进制、`0x0x` 开头的地址也被接受；
  - v3 和 v4 走同一套编码。

  这些都不是资金漏洞，但应该一律报错。
- 签名请求里的地址参数没有核对是不是本钱包地址。iOS 遇到 `[对象, 地址]` 这种参数，会把地址当成消息去签。
- 消息签名判断「是不是十六进制」不严格：Swift 接受 `+`、`-` 号，Kotlin 接受阿拉伯数字。显示的和签的是同一份字节，只是和网页本意可能不同。
- 交易参数：`data` 为 null 时没有回落到 `input`；`value` 接受十进制字符串；交易里的 `chainId` 字段被忽略。
- 广播连续失败、又查不到状态时，仍然返回成功和交易哈希。
- 日志：iOS 以公开级别记下「连接了哪个网站」；安卓正式版把交易哈希写进系统日志。
- 当前网络是全局共用的，网站 A 切了，网站 B 也能看到。
- 安卓的确认框显示原始金额字符串，没有格式化；iOS 向下取整到 5 位小数，极小金额会显示成 0。
- iOS 如果正好在界面转场时弹窗没弹出来，请求会一直挂着；安卓离开广场时，进行中的请求状态不确定。
- 断开连接的入口只在「更多」菜单里，地址栏没有「已连接」标识。

## 误报（核实后不成立）

- **「RPC 中转可以伪造 IP 绕过限流、冒用别人的 IP」**：服务器 nginx 用 `proxy_set_header X-Forwarded-For $remote_addr` 覆盖了网页自己填的请求头，而且服务器已经配好识别 Cloudflare 传来的真实访客地址。中转看到的永远是真实 IP，所以不成立。

## 已确认做对的

- 交易、消息签名、结构化签名的摘要都由内核自己算，不接受网页算好的哈希；签名结果和 ethers 逐字节一致。
- 签名的 s 值是低位规范形式，v 是 27/28。交易带链号（EIP-155），两条链之间不能互相重放。
- 拒绝 `eth_sign` 盲签、`eth_signTransaction`、部署合约、代发原始交易。
- 子框架的请求一律拒绝；`window.ethereum` 不可改写；原生调网页时，拼接的脚本里没有网页能控制的内容。
- 内核宿主没有被注入钱包，`TapekitBridge` 网页碰不到；上一轮浏览器审计的修复没有被这次改动破坏。
- 没连接时 `eth_accounts` 返回空；授权按「协议 + 主机 + 端口」记。
- 确认时和发送时用的是同一份交易数据，网页在中间改不了内容；网页给的 nonce、gasPrice 都被忽略。
- 余额检查包含「金额 + 手续费」；发送锁从重新估算一直持有到广播完成。
- 三种语言、两个平台的弹窗文字，参数个数和位置全部一致。

## 建议修复顺序

1. 高-1、高-2：固定链号；同一时刻只有一个待确认请求，按编号回答，确认键延迟。
2. 高-3、高-4、高-5：交易和结构化签名改为可读显示，加危险警告，严格校验 domain。
3. 中-1、中-2、中-5：跳转时取消请求，加频率限制，只给 https/tape 来源提供钱包。
4. 其余中危，以及低危里的格式校验。

修完后建议再审一轮。

### 低危

- EIP-712 格式校验全部改严：bool 只认 JSON 的 true/false；整数类型必须是 8 的倍数且 8–256 位，并检查数值范围；结构体名不能冒充基础类型、必须是合法标识符；字段名不能重复；十六进制必须偶数位；地址大小写混写的要通过 EIP-55 校验；v3 遇到数组直接拒绝。
- 签名请求里写了地址的，必须是本钱包地址（personal_sign、signTypedData 都检查）。
- 交易参数：data 为 null 时用 input；金额只接受 0x 十六进制或 JSON 数字，十进制字符串拒绝；交易里写了 chainId 的必须等于当前网络；网络切换请求的链号只认 0x 十六进制。
- 日志：iOS 记连接网站改为私密级别；内核里网页交易和发送成功的日志降为调试级别、不再记交易哈希。
- 网络按网站分开记（见高-1）。
- 金额显示改用内核给的精确数字，不再四舍五入或取整。
- iOS 弹窗弹不出来（没有可用界面）时当作拒绝，不再一直挂着；安卓离开广场、请求被取消时给网页回「拒绝」。
- 地址栏加了「已连接钱包」图标；未连接的网站不能切网络，菜单里也只对已连接的网站显示网络选项。
- **没有改的一条**：「广播失败又查不到状态时仍返回交易哈希」是全钱包共用的设计——这种情况下交易可能其实已经发出去了，报失败反而可能让网页重发、重复付款。现在网页交易会进「待确认」列表，用户能看到它最后是成功还是没上链。
