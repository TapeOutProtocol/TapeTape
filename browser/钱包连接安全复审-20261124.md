# 广场浏览器「连接钱包」功能安全复审（2.0.14）

日期：2026-11-24　　范围：上一轮审计（`钱包连接安全审计-20261124.md`）修复后的本机代码，未提交、未发布。

五个角色并行只读复审：
- 一、签名与内核正确性：用 ethers 6.17、viem 和一份手写的规范参考实现做了交叉对照
- 二、钓鱼与界面欺骗
- 三、资金与交易流程
- 四、网页隔离与注入
- 五、并发、滥用与隐私

下面已合并重复项。括号里是发现这一条的角色。关键几条我对照代码复核过，都属实。

## 结论

**上一轮的主体修复是真的。** 下面这些都已核实：
- 显示什么网络就用什么网络；
- 同一时间只有一个钱包弹窗，确认键要等 1 秒才能点；
- EIP-712 签名会拒绝多余字段，并且绑定链号；
- 页面跳转时作废没处理完的请求；
- 子框架用不了钱包；
- 确认的交易和实际发出去的是同一份；
- 签名编码和 ethers、viem 逐字节一致。

**但还不能发布。** 复审新发现 **3 条高危**，都在内核的「交易识别」和「签名危险识别」上：网页能让用户在看起来安全的弹窗上交出资产。另有 11 条中危、约 25 条低危。

## 高危

### 复-高-1　「授权全部 NFT」能显示成「撤销授权」（一、二、三，新引入）
- **位置**：`dapp.rs:672`，`let on = word_at(data, 1)?[31] != 0`，只看最后一个字节。
- **攻击**：`setApprovalForAll(攻击者, 0x…0100)` 会被识别成撤销（revoke-all），不标危险，也没有二次确认。
- **后果**：0.8 以前的编译器编出的合约，会把任何非 0 的值当成 true。2021 年前后 BNB 链上的 NFT 合约大多属于这种。链上实际执行的是「把全部 NFT 授权给攻击者」。
- **修法**：参数必须正好是 0 或 1；否则按「无法识别」处理，并且标危险。

### 复-高-2　参数后面多补一段，危险授权就降级成「无法识别的操作」，而且只确认一次（一，新引入；二、三也指出无法识别的调用不标危险）
- **位置**：`dapp.rs:658-676`，各分支写死了参数个数（`n == 2`、`n == 3`、`n == 4`）。
- **攻击**：`approve(攻击者, 无限)` 后面再补 32 字节的 0，识别结果就变成 None。increaseAllowance、setApprovalForAll、Permit2 授权都能这样绕过。
- **后果**：Solidity 会忽略多出来的数据，链上照样执行无限授权。弹窗只显示一行「无法识别」，不标红，也不二次确认。
- **另外**：批量调用（multicall）、NFT 安全转账（safeTransferFrom）、Seaport 等常见盗币调用，本来就落在「无法识别」里。
- **修法**：
  - 只检查参数够不够长，多出来的数据照样解码，同时标危险并写明「附带额外数据」；
  - 选择器是危险函数、但格式不对的，按危险处理；
  - 所有识别不了的合约调用，一律标红并二次确认。

### 复-高-3　「签了就能直接转走钱」的结构化签名没有警告（一、二，上一轮高-4 修得不完整）
- **位置**：`dapp.rs:562`（看类型名里有没有 permit、order、approv、delegat）、`dapp.rs:484`（看字段名）。
- **漏掉的类型**：
  - `TransferWithAuthorization`、`ReceiveWithAuthorization`（EIP-3009，签了就是直接转账）；
  - `ForwardRequest`（ERC-2771，代你执行任意调用）；
  - `MetaTransaction`；
  - `SafeTx`（多签钱包执行任意调用）；
  - 类型名里不带 order 的挂单类型。
- **实测**：这些类型签名时都不标危险。
- **显示也有问题**：
  - bytes 字段超过 64 字节会被截断，要执行的调用数据只显示前 32 字节（`dapp.rs:458`）。上一轮报告说「不截断」，不成立。
  - 金额显示的是原始整数，没有换算小数位。
- **修法**：
  - 改成「认识的无害类型才不标危险，其余一律标危险」；
  - 带 to/value/data/operation 这类字段的，按危险处理；
  - bytes 完整显示；
  - data 字段用交易识别解析后再显示。

## 中危

| 编号 | 问题 | 发现者 | 修法 |
|---|---|---|---|
| 复-中-1 | **NFT 的 approve(攻击者, 0)** 和代币 approve 是同一个函数编号，实际是把 0 号 NFT 交出去，却显示成「授权数量 0」、不标危险。NFT 的 approve 和 transferFrom 把编号显示成数量。另外，普通代币的 approve(x,0) 本来就是撤销，文字却写成「对方可转走你的代币」 | 一、二、三 | 读不到小数位，或查到合约支持 ERC-721 接口时，按 NFT 显示「NFT #编号」并一律标危险；确认是普通代币且数量为 0 时，显示「撤销授权」 |
| 复-中-2 | **网页能在弹窗里伪造「App 自己写的行」**：清洗函数保留换行，字符串没有转义。签名字符串、网站自称的名字、消息签名、合约回滚说明、代币名，都能写出「✅ 安全检查通过」「网络：X Layer」「spender: 0x…」这样的假行。换行之间夹一个空格，就能绕过空行压缩（实测 101 个换行全部保留）。U+2028/2029、U+3164、U+2800、U+00AD、U+FE0F、Tag 字符等都没被标出 | 一、二 | 来自网页或合约的文字：换行替换成可见符号，字符串用 JSON 转义并加引号；按 Unicode 类别（Cc/Cf/Zl/Zp/默认可忽略字符）统一标出；限制总行数；回滚说明放到视觉上明显隔开的区域 |
| 复-中-3 | **EIP712Domain 的字段类型不强制**：网页可以把 verifyingContract 声明成字符串，这一栏就能填任意内容（任意换行、反向文字、任意长度），可以伪造行，或把危险警告挤出屏幕。chainId 也能声明成字符串 | 二、一 | name/version 必须是 string，chainId 必须是 uint256，verifyingContract 必须是 address，salt 必须是 bytes32；不对就拒绝；version、salt 也要显示出来 |
| 复-中-4 | **iOS 的报错提示不在「单弹窗」保护里**：签名格式错误（第 265 行）、交易失败（第 287、301 行）时直接调 `Alerts.show`，叠在正开着、已经可以点的钱包确认框上面。网页连发几十个，用户连点「好」时可能误点到下面的确认键。发交易走的估算不经过内核限频，网页能借这条路无限消耗中转额度 | 二、四、五 | 报错也走同一个弹窗位置，已有弹窗时不弹，只把错误回给网页；估算这条路也要计入限频 |
| 复-中-5 | **网页能反复弹窗，把 App 锁住**：被拒后冷却只对「连接」生效，签名、交易、切网络被拒后可以立刻再弹。网页自己的 `while(1) alert()` 也一样。冷却和限频都按完整来源计，换子域名或端口就能绕过 | 二、五 | 所有需要弹窗的请求都按网站计拒绝次数，到次数就冷却；冷却按主域名（eTLD+1）计；加一个全局冷却；网页弹窗连续 3 次后提供「禁止此网页再弹窗」 |
| 复-中-6 | **「连点游戏」能绕过 1 秒延迟**：页面诱导用户在确认键的位置连续点击，确认键一变成可点就被点中；二次确认的按钮在同一个位置，也会被连点点中 | 二 | 只认确认键变成可点之后才开始的按压；检测到连点就重新计时；二次确认把按钮换到别的位置，或改成长按 |
| 复-中-7 | **连接之前仍能认出 TapeTape**：(1) 钱包的通信接口对所有框架可见（iOS 的消息处理器、安卓 `"*"` 规则下的 walletBridge），往里发一条消息会收到固定的英文回复；(2) 页面自己调用 `__walletEvents.emit('accountsChanged',['0x1'])`，就能触发「TapeTape」的广播；(3) 未连接时 eth_chainId 也回 0xc4；独有的错误文字；内核原话会转发给网页 | 四、五 | 不是主页面、或来源不允许的消息，直接丢弃不回复；事件改走通信接口推送，不挂在 window 上；广播只能由原生确认连接后触发；未连接时 chainId 回 0x1 或拒绝；错误文字改成和 MetaMask 一样的通用写法 |
| 复-中-8 | **交易可能已经发出，却报失败或「用户拒绝」，引导用户重发、重复付款**：中转超时、公共节点回 already known、再查一次没查到，就报失败，而且不记待确认；安卓发送途中页面跳转，协程被取消，网页收到 4001，但内核任务取消不了，照样广播 | 三、五 | 签名后、广播前先写待确认记录（钱包自己的转账就是这么做的）；already known、nonce too low 这类回复按「可能已发出」处理；结果不明时弹窗写「可能已发出，请到钱包查看，不要重复发送」；进入发送阶段后不响应取消 |
| 复-中-9 | **序号取各节点最大值，会被任意一个节点的异常大值控制**：节点回一个特别大的序号，之后钱包所有交易都卡死；签好的「未来序号」交易会在将来某个时候突然生效 | 三 | 本地持久化记录已用过的序号；取值为 max(各节点最小值, 本地已用 + 1)；节点给的值比本地大太多时拒绝发送；两个节点并发查询 |
| 复-中-10 | **「链上网站，内容已核对」读起来像官方背书**：谁都可以开通一个链上名字放钓鱼页，页面还能从链外拉数据画任意界面。链上网站某一页没核对上时，标签写「普通网站」，和地址栏显示的链上名字互相矛盾 | 二 | 改成「链上网站（文件与链上一致，不代表网站可信）」；没核对上的单独写「链上网站，本页未核对」 |
| 复-中-11 | **类型链太深会让 App 闪退**：`deps` 递归没有深度上限，2 万个首尾相连的类型（约 780KB）实测栈溢出，无法捕获；`encode_type` 的耗时随类型数平方增长。前提是网站已经连接 | 一（原报低危，我上调了：已连接的网站能稳定让 App 闪退） | 限制类型数量（≤64）和 JSON 大小；改成不递归的写法 |

## 低危

**内核**
- 字符串字段可以写出假的「字段: 值」行（并入复-中-2）。
- personal_sign 只有「32 字节十六进制」才判成盲签；看起来像乱码、但恰好是合法 UTF-8 的内容不会警告。
- 代币名、网站自称的名字是对方自己说的，没有标「合约自称」。
- 未知代币读不到小数位时，按原始整数显示，没有说明是最小单位。
- 节点返回的 gas 乘 6/5（`chain.rs:400`），以及钱包转账、红包里的 gas×价格，都没有溢出检查。
- 确认时用的链和发送时用的链没有在内核里绑定，全靠两端传同一个值（两端目前是对的）。可以做成一次性票据。
- 网页交易在待确认列表里一律记成「0 原生币 → 代币合约」，代币授权和转账显示得有误导；iOS 还把它放在「提现」标题下。
- 广播失败时仍以 warn 级别把交易哈希写进日志（`chain.rs:457/462/466`），上一轮说的「不再记哈希」只在成功时成立。
- 限频表超过 500 条时会整表清空。
- 和 MetaMask 不兼容的小地方：`"-0"`、超过 2^53 的整数、`0X` 前缀；递归类型的签名和 viem 结果不一致（待核实）。
- EIP-712 金额没有换算小数位，无限额度不显示「无限」；Permit2 授权不显示到期时间。

**iOS**
- `cancelAll` 不释放 busy，也不取消正在跑的任务：旧请求卡在估算时，新页面会一直「忙」；还可能在新页面上弹出旧网站的二次确认（点了也不会签名）。
- 弹窗没弹出来时，请求会一直挂着；网页 alert 弹出失败时，计数漏减，可能让钱包一直拒绝，WebKit 也可能闪退（待核实）。
- 网址主机名带大写时，两处来源比对对不上，钱包用不了（只会误拒，不会错放）。
- 地址栏在跳转真正完成之前就改了显示（待核实）。
- personal_sign 遇到 [对象, 地址] 参数时，会把地址本身当消息签：会显示盲签警告，但和安卓行为不一致。

**安卓**
- 取消后旧协程的 finally 会误清 busy，可能出现两个并发估算，但只会有一个弹窗。
- 按钮回调没有绑定「自己是哪个弹窗」。
- 表单 POST 到 `http://xxx.tape` 不会触发跳转拦截，地址栏会显示成链上名字（钱包不受影响）。
- 「离开本页？」确认框（beforeunload）没有接管（待核实）。

**两端**
- 子框架里的 `web+tape:` 链接、`window.open` 能把整个页面带走，可以绕过框架的沙箱；iOS 的 `web+tape://` 不检查名字。
- 二次确认写的是「〈网站〉可以动用你的资产」，真正拿到权限的是签名里的被授权方。
- 网页自己的弹窗只改了标题，外观和钱包弹窗一样，可以照抄钱包的正文。
- 普通网站的名字显示去掉了端口；超长的多级子域名没有突出真正的主域名。

## 核实为真的上一轮修复

- 高-1：请求一开始就固定网络，估算、显示、发送都用它（三、五）。
- 高-2：钱包弹窗同时只有一个，确认键要等 1 秒才能点（两端），二次确认的按钮是红色（二、五）。例外是复-中-4 说的 iOS 报错提示。
- 高-4/高-5：只显示签进去的字段；多余字段拒绝；缺失的字段报错，不会当 0 签；domain 字段必须和声明一致，必须带当前链号；补出的 EIP712Domain 和 ethers 一致（一）。
- EIP-712 编码与 ethers、viem 逐字节一致（结构体数组、多维数组、int8/int256 的边界、bytes1、空 bytes、salt 等）；v3 拒绝数组（一）。
- 签名：v 为 27/28，s 是低位规范形式，交易带 EIP-155 链号；摘要一律由内核算（一）。
- 确认的交易和发出的交易是同一份；手续费上涨超过一半就停，判断方向正确；gas 封顶为估算的 2 倍；带溢出检查；余额检查；发送锁覆盖钱包所有写操作（三）。
- 格式校验全部改严；EIP-55 校验正确（一）。
- 页面跳转、换网站、离开广场时作废请求；签名和发送前都重新检查（四、五）。
- 子框架请求被拒；来源白名单加上与当前网址比对；data:/blob: 主页面被拦；provider.js 三份逐字节一致；原生调网页的脚本里没有网页能控制的内容；内核宿主仍然隔离（四）。
- 限频、getLogs 限制、连接冷却的逻辑成立，但能绕过（见复-中-4、复-中-5）。
- 三种语言两端的弹窗文字，参数个数和顺序一致（二）。

## 建议修复顺序

1. 复-高-1、复-高-2、复-中-1：交易识别。都在 `decode_call` 一处，改动小，收益最大。
2. 复-高-3、复-中-2、复-中-3、复-中-11：签名的危险识别、文字清洗、domain 类型强制、深度限制。
3. 复-中-4、复-中-5、复-中-6：弹窗互斥、全面冷却、连点防护。
4. 复-中-8、复-中-9：广播结果不明时的处理、本地记录序号。
5. 复-中-7、复-中-10 和低危。

审计用的测试和交叉对照脚本在会话临时目录（`scratchpad/core/…/dapp.rs` 末尾的 audit 测试、`scratchpad/x/cases.mjs`、`scratchpad/x/ref.mjs`），重启后可能会被清掉。

| 复-中-4 | 两端所有弹窗（钱包确认、报错提示、网页 alert/confirm）共用一个位置，同时只有一个；报错提示也要等用户点掉；发交易前的估算也计入每个网站的限频 |
| 复-中-5 | 所有需要弹窗的请求被拒都计数：同一网站（按主域名，链上网站按名字）连续拒 2 次冷却 5 分钟；2 分钟内拒 6 次，所有网站暂停 2 分钟。网页自己的弹窗每页最多 3 次，之后直接当取消 |

| 复-中-11 | EIP-712：JSON 不超过 64KB，类型不超过 64 个、每个类型不超过 64 个字段，递归类型直接拒绝，依赖遍历改成不递归的写法。单元测试：5000 个首尾相连的类型被直接拒绝 |

### 低危

| 范围 | 怎么修的 |
|---|---|
| 内核 | • 超过 2^53 的 JSON 数字拒绝（必须写成字符串）<br>• 接受 `-0`（按 0 处理）和 `0X` 前缀<br>• gas×6/5、钱包转账和红包里的手续费乘法都加了溢出检查<br>• 广播失败日志不再带交易哈希<br>• 限频表满了只清理一分钟没动静的网站<br>• 确认票据把「链号 + 交易内容 + 手续费」和本进程的随机密钥绑在一起，发送时核对<br>• 网页交易在待确认列表里带「网页交易」标记 |
| iOS | • 跳页时立即释放「忙」状态、取消进行中的任务，过期的二次确认不会再弹出<br>• 弹窗 1 秒内没真正显示出来，当作拒绝<br>• 网页弹窗不再单独计数，计数漏减的问题随之消失<br>• 来源统一转小写<br>• 地址栏和绿盾在页面真正显示（didCommit）后才更新<br>• `window.open` 只接受主页面发起的，`web+tape://` 只接受主页面发起、名字是链上数字名字的<br>• personal_sign 参数必须都是字符串<br>• 提现页不列网页交易 |
| 安卓 | • 「忙」状态记在当前页面上，旧任务结束时不会误清<br>• 按钮只回答自己那个弹窗<br>• `http://*.tape` 的所有请求（包括表单 POST）一律 403，地址栏只把 https 的 `.tape` 显示成链上名字<br>• 接管「离开本页？」确认框，直接允许离开<br>• 子框架的 tape 链接不再处理<br>• 待确认列表里的网页交易显示「网页交易 → 合约」 |
| 两端 | • 二次确认写的是签名或交易里真正的被授权方 / 收款方<br>• 网页弹窗正文第一行标「网页内容，不是 TapeTape 的提示」<br>• 普通网站名把主域名放在前面，带端口时写出端口 |

### 有意保留、没有改的

- **未连接时 `eth_chainId` 仍然回当前网络（默认 0xc4）**：网页连接前要靠它判断该切哪条链，改成拒绝或假值，会让大量网页连不上。主页面本来就能看出「这里有钱包」，这一条只会多暴露「默认在 X Layer」。
- **iOS 提现页不显示网页交易**：避免被当成提现。安卓的待确认列表里显示，并标明「网页交易」。

### 测试

- 内核单元测试 74 项全部通过，新增的覆盖：
  - NFT、布尔、多余数据的交易识别；
  - 授权转账、代执行、登录签名的危险判断；
  - 字符串转义、隐形字符、空行绕过、超长消息；
  - domain 类型强制、非标准字段；
  - 递归类型、类型过多、大数；
  - 日期换算、确认票据、序号选择。
- 安卓模拟器（2.0.15）实测：
  - 主页面和框架里都找不到任何钱包、TapeTape 相关的全局对象；
  - 请求经私有端口正常往返，错误都是通用说法；
  - 连接弹窗标签正确；
  - 连点期间确认键一直是灰的，停下后才亮；
  - 授权转账签名标红、显示日期，二次确认写出收款地址、按钮竖排；连点的人最后点到的是「取消」；
  - 连续拒绝两次后，第三次请求直接被拒，不再弹窗；
  - 网页 confirm 标「网页内容」，连弹 4 次时第 4 次自动取消。
- iOS：
  - 编译通过；
  - 用同一套 WebKit 写了独立测试程序，验证了脚本世界之间的通道：请求和拒绝都能往返，网页和框架都看不到消息处理器；
  - 模拟器没有账号，钱包弹窗流程没有走（规则和安卓一致，但没有实测）。
- 两端都没实测的：
  - 交易确认弹窗（测试钱包没有余额）；
  - 真实链上的 NFT 合约判断（ERC-165 查询）。

### 建议

改动量仍然很大：内核约 1300 行，两端钱包再次重写，通道机制也换了。建议在真机上（至少一台有余额的测试钱包）把交易流程走一遍，再做一轮针对新通道的复审。
