# 红包合约审计记录

审计对象：`src/TapeTapeRedPacket.sol`。最终版本的指纹（部署页顶部会显示，部署前请当面核对）：

- 字节码 sha256：`0ffe1b53e51c2922261430c2d4a47a3fac9128dbda904e99f08d6ba4ae18398f`
- 源码 sha256：`f75b267395f05278a617636cb0749198366715dfe6d44aa7ea42538908126762`
- 编译：solc 0.8.28，evmVersion paris，优化 200 次

三轮审计由互不知情的独立审计员完成：每轮只拿到代码和需求，不看前几轮的结论。各轮的概念验证测试保存在 `test/audit/`、`test/audit2/`、`test/audit3/` 下，最终 `forge test` 共 102 条，全部通过。

## 第一轮（2 名审计员：攻击者视角、规格与对接）

结论：没有阻断或高危问题，可以部署。修复了以下各条：

| 发现 | 级别 | 处理 |
|---|---|---|
| 1:1 转账，发送者可以在对方领取前自己领回 | 中 | 加 `recipient`，转账只有收款人能领 |
| 创建者被代币拉黑后退不了款 | 低 | `refundRedPacket(id, to)` 可指定收款地址 |
| 主人放弃所有权后，手续费永久锁死 | 低 | `renounceOwnership` 禁用 |
| 净额 > 2^255 时领取溢出 | 建议 | 先除后乘 |
| 红包 ID 可以带控制字符、方向反转字符 | 建议 | 只允许 `[0-9A-Za-z-]` |
| 随机金额可以预测、可以回滚重试；事后才变余额的代币；误转的钱取不回 | 低 | 写进 README「已知局限」 |
| 客户端：判断有效时，拿扣费前金额去比扣费后金额（旧合约线上已出错，因为现在费率是 20‰） | 高（客户端） | 新客户端改为「总额 = 净额 + 手续费」 |

## 第二轮（1 名审计员，含 33 个变异测试）

结论：合约没有阻断或高危问题。33 个变异中，32 个被测试抓到；剩下 1 个是等价变异，改了也不影响行为。修复了以下各条：

| 发现 | 级别 | 处理 |
|---|---|---|
| 部署页同时连过两个钱包后，可能把交易发到错误的链，并把地址记在错的链名下 | 中（部署页） | 只听当前钱包的事件；发送前当场核对链号和账户；交易带上 chainId；上链后再核对一次 |
| 转账仍要领取签名，收款人丢了聊天记录就领不了 | 建议 | 设了收款人的转账不再要求签名 |
| 一个群成员可以在一笔交易里抢光整个红包 | 中（设计取舍） | 无法低成本消除，在 README 写明 |
| 主人地址没有校验和检查；记录正式地址时不核对主人；手续费输入框留空按 0 部署；交易被加速后误报超时 | 低 | 全部修复 |

## 第三轮（1 名审计员，合约 + 客户端 + 部署页 + 文档）

结论：合约和部署页没有阻断、高危、中危问题，可以部署。审计员独立重新编译源码，结果与部署页里的字节码逐字节一致。客户端的两条中危已修：

| 发现 | 级别 | 处理 |
|---|---|---|
| 客户端发送时把当场读到的费率当作上限，主人调高费率，用户察觉不到 | 中（客户端） | `chain.rs` 按链写死可接受的费率；链上费率更高时，报 `fee-too-high` 并停发 |
| 收到的卡片在链上核对之前就显示「可领取」，可以被伪造卡片骗 | 中（客户端） | 收到后先设为不可领取，界面显示「正在链上核对…」 |
| 金额乘法没有防溢出 | 低（客户端） | 改用 `saturating_mul` |
| 转账卡片给收款人显示的是含手续费的总额 | 低（客户端） | 未改，记为待办 |
